## 1. TRANSFER VALIDITY

A message is a valid transfer listing only when it clearly describes either:

- a traveler offering to carry goods, or
- goods/cargo that need to be transported.

Do not classify a message as a transfer merely because it contains a flight, airline, airport, route, date, city pair, cargo-related word, or the word "post".

Interpret the complete message.

If there is no clear transfer intent:

`transfer_role = null`

A record with `transfer_role = null` must be rejected by the application and must not be saved as a transfer listing.

---

## 2. TRANSFER ROLE

Allowed values ONLY:

- `passenger`
- `shipper`
- `null`

### passenger

Use `passenger` when the author is traveling and is offering or indicating the ability to carry goods for another person.

Use this when the message clearly indicates that the author is traveling and can carry, accept, or transport another person's goods.

### shipper

Use `shipper` when the author has or owns goods and wants another person or service to transport them.

### DECISION PRIORITY

1. Explicitly offering to carry another person's goods → `passenger`
2. Clearly traveling and accepting/offering cargo → `passenger`
3. Clearly has goods and needs someone to transport them → `shipper`
4. Meaning remains ambiguous → `null`

Never determine the role from a single keyword.

A flight number, airline, airport, route, date, or cargo description alone is insufficient.

---

## 3. ROUTE

`origin_city` = departure, loading, or source city.

`destination_city` = arrival, unloading, or target city.

Preserve the direction stated by the source.

Never reverse origin and destination.

Each city field must contain exactly ONE city.

If multiple cities appear on one side, select the primary/base city only when the source clearly provides enough context to identify it.

Prefer:

1. explicit departure/arrival point
2. main route city
3. primary/base metropolitan city

If multiple independent routes exist and no single route is clearly dominant, use `null` for ambiguous route fields.

Never concatenate multiple cities.

---

## 4. CITY NORMALIZATION

Return city names in their standard internationally recognized English/Roman form.

Translate known city names to their standard English/Roman form rather than transliterating character-by-character.

Each city field must contain only the city name.

Do not include:

- country
- province
- airport code
- flag
- emoji
- URL
- hashtag
- punctuation

## 5. COUNTRY AND PROVINCE

Return countries as ISO 3166-1 Alpha-2 uppercase codes.

Infer the country only when it can be determined confidently from the source or clearly identifiable city.

Otherwise use `null`.

Never return country names, flags, or UN/LOCODE.

Extract province only when explicitly stated or confidently identifiable.

Never guess a province.

---

## 6. DATES

Extract explicit travel, departure, arrival, delivery, or shipment dates.

Format:

`YYYY-MM-DD`

The application provides the current date.

If a date has no year, assume it belongs to the current month unless the source explicitly indicates another year.

Recognize Persian/Jalali dates and convert them to Gregorian ISO format.

Recognize Persian digits, Arabic digits, English dates, Persian month names, and common spelling variations.

If a date is clearly associated with a flight or travel route and no separate arrival date is stated, treat it as `departure_date`.

Never invent an arrival date.

A date alone does not determine `transfer_role`.

## 7. TRANSPORT TYPE

Allowed values ONLY:

- `air`
- `ground`
- `sea`
- `null`

Use `air` when the message clearly describes air transportation.

Use `ground` when it clearly describes road or rail transportation.

Use `sea` when it clearly describes maritime or sea transportation.

Do not determine transport type from an ambiguous or isolated word.

`post` alone does not determine the transport type.

Never create another value.

### quantity

## 9. PRICE

Extract `price` only when a monetary amount is explicitly stated.

Never estimate or calculate the price from route, distance, weight, quantity, cargo, or any other information.

Determine `currency` using this priority:

1. If the currency is explicitly stated in the message, use that currency.
2. If the currency is not explicitly stated, determine the most likely currency from the combination of `origin_country` and `destination_country`.
3. If the route does not provide enough information to determine the currency confidently, use `null`.
4. Never invent a currency when the country/route context is ambiguous.

The currency must represent the currency in which the stated price is being offered.

Do NOT convert the price to another currency.

Do NOT change the numeric `price` based on the inferred currency.

Use standard ISO 4217 currency codes.

If no price is stated:

`price = null`
`currency = null`

If a price is stated but its currency cannot be determined confidently:

`price = <stated amount>`
`currency = null`
